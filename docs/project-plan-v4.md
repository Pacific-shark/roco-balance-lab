# 洛克研究室：从配队探索到个体评价

2026-10-16 · 私人面试项目 · v0.4

**实施更新：** 下文保留 v0.4 轻量工作台的设计与任务管理说明。新的玩家视角 PPO、实体 MLP／GRU、局部能力补训和冻结配队研究已经执行，见 [当前训练实现](learning-pilot.md) 与 [23 次实验及 960 局配队对照结果](learning-results-2026-10-16.md)。新 PyTorch 流程使用命令行、工作台只读展示结果；下文旧任务系统的暂停／继续不适用于新训练器。完整机制、全量精灵和最优培养仍未完成。

核心问题：在同版本、同规则、同预算的六人对战中，一只精灵能承担什么角色，在哪些队伍中有效，优势是否依赖不合理的数值、技能分配或补盲？

目标使用者是希望检验平衡假设的产品与游戏策划。工具交付配队、对局证据和可检验的原因，不把一个总分或排行榜当成解释。项目成功的标准是：另一位使用者能够复现一次研究、找到反例，并判断调整是否保留了玩法特色。

## 1. 本轮交付与边界

| 模块 | 本轮可运行内容 | 尚未完成 |
| --- | --- | --- |
| 数据库 | SQLite；固定社区资料快照；形态、技能／特性、学习表、术语、进化、机制证据分表；版本哈希 | 全字段最新官方有效性认证；所有形态模式准入 |
| 研究队列 | 按图鉴编号浏览最高常规形态，区分首领、低阶；搜索与资料查看 | 未支持精灵的完整战斗执行 |
| 任务系统 | 单工作线程；训练局数和累计时限；每100局检查点；暂停继续；报告持久化 | 跨机器调度、GPU训练集群 |
| AI | 两份独立参数的策略梯度；当前、历史和规则对手；研究对象固定一席，其余配置自由生成 | 现行完整机制、玩家可见信息迁移、跨种子能力认证 |
| 配队探索 | 一代候选生成、适应训练、留出验证筛选、至多3套有成员差异的队伍 | 多代联合搜索、所有培养边界、同定位替换后等预算重训 |
| 评价 | 独立配置测试、逐局数据、冻结策略的特性移除对照、五维证据状态 | 全环境强度与正式设计结论 |
| 前端 | 研究队列→预算配置→任务进度→证据报告；沿用旧图鉴和原型入口 | 完整策略回放可视化及批量研究看板 |

当前可执行环境仍是10形态、42技能的旧机制子集。新数据库包含更多资料，不等于这些机制已经执行。界面、报告、接口均区分“流程验证”和“正式强度研究”；后者在规则和能力检查通过、正式适配器实现前拒绝启动。

“草魔法换下后停止回血”作为用户提出的待验证假设保存，不冒充已核准规则；效果是否保留、后台倒计时、重新上场后的触发另列。原型没有草魔法执行器，因此本轮实验不会利用这个假设制造结果。

## 2. 数据库与版本

使用仓库内固定快照，首次启动导入本地SQLite。无需数据库账号、模型API Key或云资源。数据库位于 `.local/research.sqlite`，不提交GitHub；可由快照重建基础资料。BWIKI衍生资料保留修订、来源和CC BY-SA 4.0许可，不把采集时间写成游戏生效时间。

| 表 | 内容 | 约束 |
| --- | --- | --- |
| snapshots | 数据版本、来源修订、哈希、入库时间 | 内容变化生成新快照，保留旧版 |
| entities | 各形态、技能／特性、学习表、术语、进化原始字段 | 快照＋类别＋实体ID联合主键 |
| roster | 编号、最高形态分类、模式合法状态、原型支持状态 | 合法与能执行是两个字段 |
| mechanics | 规则主张、证据、用户确认、假设、待核验项 | 未确认数值不自动补默认值 |
| experiments | 对象、角色假设、预算、数据与执行代码哈希、状态、检查点、报告 | 同一实验的版本和预算不可静默改变 |
| metrics | 分批完成量、更新次数、决策数、阶段指标 | 与检查点在同一事务中保存 |

未来正式构筑记录应包含六人名单、天分、性格、唯一血脉、四技能顺序、整队共鸣与首领分支。不能把各血脉技能合集当作一套合法配招。未来的逐字段版本差异也要记录公告生效日与替代关系。

## 3. AI训练与配队搜索

完整目标流程：按编号选研究对象→生成合法六人候选→两个AI学习操作→验证池筛选并变异候选→再适应训练→保留不同用法→冻结队伍与策略→测试与归因。

每个研究对象占一席，不强制当核心。进攻、防守、支援、轮转、针对性反制都是待检验角色，允许兼任；不会通过额外奖励它的伤害或出场率制造“核心价值”。团队胜负是主要目标，过程奖励只用于学习效率，并应做去除奖励的对照。

本轮采用现有独立策略梯度基线，不调用聊天模型决定行动。A、B各自更新参数，混合当前策略、历史快照和规则对手。启发式初始权重明确标注，不能把初始能力计作学习提升。算法背景见[策略梯度说明](https://spinningup.openai.com/en/latest/algorithms/vpg.html)。

当前任务以100局为一批。批内运行历史池，批间保存两方权重并重置回报基线与历史池；连续运行和断点继续都按相同批次规则执行。它是明确的分批训练，不宣称与单次长训练逐步等价。数据、代码或任务配置变化需新建实验，不能直接接续旧成绩。

后续若线性策略无法通过支援、资源规划、轮转等能力题，再引入带历史输入的循环策略与PPO等候选，比较学习曲线、稳定性与算力成本；不会仅因算法名字更复杂就替换。旧原型读取完整配置，正式适配器必须切换到核准后的可见观察和历史，禁止泄漏隐藏配置或未来行动。

### 防止把搜索误差当作强度

- 同一角色的对象使用相同基础预算、统一对手分布；追加预算须单独报告。
- 训练、验证、测试按完整构筑去重；测试只用于锁定后的评价。
- 先过合法动作、轮转、资源、支援与机制记忆题，再给个体下结论。
- 至少多个独立训练种子；若结论随种子反转，报告不稳定而非取最好的一次。
- 用“本版本、本范围、本预算内发现的配队”，不称全局最优。

本轮只执行一代候选和少量留出配置，用于检验工具链。不是完整搜索方法已验收。

## 4. 五维评价：原始证据先于分数

| 维度 | 主问题 | 数据与对照 | 不能偷换的结论 |
| --- | --- | --- | --- |
| 竞技表现 | 哪些队伍和对位有效？ | 测试得分、对手分布、最差对位、跨种子稳定性 | 单队胜率不等于个体强度 |
| 个体贡献 | 换掉它会失去什么？ | 同定位替换；固定策略与等预算重新适应分开 | 特性移除差值不等于个体贡献 |
| 玩法特色 | 特性是否改变决策与资源流？ | 特性／关键技能消融、触发机会、实际收益、回放 | 特色明显不等于必须高伤害 |
| 反制与代价 | 优势是否有可获得的反制？ | 补盲前后对位变化、技能槽与共鸣机会成本、对手重训 | 未找到反制不等于不存在反制 |
| 设计一致性 | 实际玩法是否符合设计假设？ | 有来源的设计目标、观察行为、人工复核 | 研究者假设不冒充官方设计意图 |

不默认加权成总分。证据不足保持空缺。真正的风险解释要指向可干预原因：某招分配到该精灵后的收益、补盲是否抹掉关键反制、资源循环是否缺少代价、协同是否被少数搭档垄断。

对照分两层：先冻结双方策略改变单项机制，观察直接敏感度；再给双方相同预算重新探索，判断适应后是否依然失衡。本轮实现前一层特性对照，后一层保留在既有研究原型与下一阶段方案中，不能混为已完成。

胜计1、平计0.5、负计0时称“对局得分”，不叫纯胜率。多座位重复不视作独立样本；按对手配置聚类估计区间，少于10组不展示区间。即使达到10组，区间也不覆盖单一训练种子的偏差，不能冒充全环境置信度。

## 5. 前端与面试演示

主页强调研究对象和实验预算，避免塞满大屏数字。数据队列按真实图鉴编号排列；主按钮创建一个有范围、有预算的任务。任务进行中显示已完成局数与阶段，允许暂停；报告能下载配置、版本、逐局证据与限制。

演示顺序：解释一个设计问题→查对象资料与未决机制→选一项角色假设→运行小预算流程→读取冻结测试与特性敏感度→指出目前不能下的结论→提出下一项能区分原因的实验。

产品能力体现在：定义可验证的问题，分清数据可靠性与算法能力，制定可比较的实验预算，解释指标局限，把异常转成下一步验证，而不只是展示一个会打架的AI。

## 6. Token与运行成本

训练与评估：0次大模型API调用、0 API token。全部行动由本地算法计算。这里不包含开发对话和界面概念生成的消耗，也不意味着CPU、电力和运行时间为零。

默认100局训练、60秒累计运行上限、3个候选、单线程任务。最大2000局、600秒；运行时限覆盖训练、验证、测试及对照。达到时限停止并保留最近完整检查点，未完成批次可能需要重算。每秒本地写一次用时，前端有活动任务时每4秒读状态；这些都不调用大模型。

不持续把日志喂给AI。人工或Codex只在一个阶段结束时读摘要、失败原因和少量关键回放。GitHub保存代码与固定公开资料；不自动部署、不在Actions上长时间训练。

## 7. 下一阶段的放行条件

1. 针对首批对象补齐共鸣、首领化、换人和完整效果依赖；所有未知路径显式拒绝执行。
2. 用当前版本逐事件样例核准结算与可见信息；反例也要通过。
3. 角色能力题通过，多个种子优于冻结基础策略，且无无效换人等奖励漏洞。
4. 外层扩展多代配队／配招／培养搜索，保留合法性证据；不同对象同预算。
5. 加入替换、技能补盲和双方重训对照，再给五维形成有依据的策划判断。

当前阶段可用于演示产品方案与可复现工程；尚不能用于对正式服精灵发布强度结论。
